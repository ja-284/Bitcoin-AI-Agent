# Backend contract, version 1

What the backend promises to tell a frontend, and — just as importantly — what it promises the
frontend will never have to work out for itself.

Produced by `agent/api/state.py`:

```bash
python -m agent.api.state --pretty
```

Read-only. It never writes, so no frontend request can affect the live record.

## The one rule this exists to enforce

> **A number that is not a validated probability must not be able to look like one.**

The backend holds three very different kinds of number, and a screen showing "87%" next to a
BUY makes them look identical:

| number | what it really is |
|---|---|
| the BUY/HOLD/SELL signal | a rules-based score with **no demonstrated predictive value** (E001, E017) |
| the confidence figure | a **heuristic** about whether the categories agree and the data was complete — not a probability, and it carries no information about whether the signal turns out to be right |
| the move-size probability | a **calibrated probability** that the next hour's move exceeds 0.25%, in either direction, currently a research shadow record. Most of its skill is knowing how volatile the market is right now — which a plain average of recent hours also captures — and the share of hours that clear 0.25% has itself ranged from 34% to 68% across years (E019, E021). Both facts are in `limitations`. |

So every quantity arrives as an object, never a bare number:

```json
"confidence": {
  "value": 0.969,
  "kind": "heuristic",
  "is_probability": false,
  "meaning": "A consistency and completeness estimate, not a probability. ...",
  "components": {"agreement": 0.939, "completeness": 1.0}
}
```

A UI that renders `meaning` alongside `value`, and that checks `is_probability` before using the
word "chance" or "probability", cannot overstate what the backend knows. A UI that ignores those
fields is choosing to overstate it, and that choice is visible in code review rather than buried
in someone's assumption.

`agent/api/state.py` is tested for exactly this: one test walks the whole structure and asserts
that **the only** field flagged `is_probability: true` is the calibrated move-size probability.

## Structure

| key | contents |
|---|---|
| `contract_version` | `"1"`. Changes when a field changes meaning or disappears. New fields alone do not bump it. |
| `generated_at` | when this snapshot was assembled (UTC, ISO 8601) |
| `pipeline_version` | the running backend version |
| `latest` | the newest prediction — see below — or `null` if none exists |
| `move_size` | the calibrated probability, or `{"available": false, "reason": ...}` |
| `recent_outcomes` | realised returns per horizon; raw numbers only |
| `health` | `ok` / `degraded` / `stale` / `no_data`, with the specific problems named |
| `limitations` | plain-English sentences that should be reachable from any screen |
| `trading`, `not_financial_advice` | the analysis-only boundary, stated in the data |

### `latest`

`as_of` (the reference candle), `information_cutoff` (nothing later than this influenced the
prediction), `data_fetched_at`, `age_hours`, `hours_since_candle_closed`, `price`,
`price_source`, `price_is_estimated`, `signal`, `signal_evidence`, `overall_score`,
`confidence`, `categories`, `news`, `explanation`, `explanation_status`, `explanation_role`,
`versions`.

Three fields are there specifically to prevent a misleading screen:

- **`signal_evidence`** travels with every signal, whatever its value. It says in plain words
  that the signal has not been shown to predict anything, and names the experiments. If the
  evidence ever changes, it changes here, once.
- **`categories[].available`** distinguishes *"this category was computed and came out neutral"*
  from *"this category could not be computed"*. A weight of 0 means the second. Showing an
  unavailable category as a neutral score is the single easiest way to mislead a reader.
- **`explanation_role`** states that the written explanation is produced *after* the decision and
  never changes it. The explanation is generated by an LLM; the decision never is.

### `move_size`

Present only when a shadow row exists and succeeded. `probability` is the one calibrated number
in the contract. `status` records that it is a research shadow record that has never influenced
the signal, and that the sealed holdout has not been opened.

### `health`

Staleness is **not** defined in the contract. `agent/healthcheck.check` owns that definition —
hours since the reference candle *closed*, allowance of 2 hours — and the hourly self-check, the
watchdog and this contract all call that one function. They cannot drift into disagreeing about
whether the system is healthy. (They briefly did during development, which is why it is now one
function and a test pins the behaviour just before an hourly run.)

## What the frontend must not do

- **Do not recompute research logic.** No indicators, no scoring, no thresholds, no calibration.
  If a number should exist, it belongs here.
- **Do not turn the signal into advice.** It is not advice, and the evidence says it does not
  predict.
- **Do not round the confidence into a percentage and call it a chance.**
- **Do not hide `health` problems**, missing news or fallback prices. Degradation that is invisible
  is indistinguishable from a system that is working.
- **Do not add a "buy now" affordance.** The backend places no orders and holds no funds; a UI
  implying otherwise would misrepresent it.

## Transport — not decided yet, deliberately

The contract is defined and tested; how it reaches a browser is a separate choice, and making it
now would be guessing. The three realistic options:

1. **The hourly job writes the assembled state into a one-row table**, and the frontend reads that
   row from Supabase. No new service, no new server to keep alive, and it fits how everything else
   in this project already works. The cost is that the state is an hour old between runs, which
   matters only for `health` and `age_hours`.
2. **A small read-only HTTP endpoint** calling `backend_state()` on request. Always current; adds a
   service that has to be hosted, monitored and secured.
3. **The frontend reads the tables directly** and does the labelling itself. Cheapest to start and
   the worst of the three: it puts the honesty rules in the UI, where they will drift.

Recommendation: **option 1**, and only move to option 2 if a screen genuinely needs sub-hour
freshness. It should be added the same way the shadow step was — after the live record is written
and self-checked, so that a failure in it can never cost an hour of the live record.

## Compatibility

Within version 1: fields may be **added**; existing fields keep their names and meanings. Anything
that removes a field or changes what one means bumps `contract_version` to `2`, and both versions
are documented before the old one is withdrawn.
