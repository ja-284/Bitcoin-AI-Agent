# Reporting contract v1: read-only statistics over the live record

**Status: built 2026-09-27, backend only.** There is no UI, no dashboard, no scheduler and no published
endpoint. This document is the contract a future frontend's statistics page will consume.

```
live hourly system  ->  authoritative database records  ->  agent/reporting (read-only)  ->  future UI
```

Nothing flows back. The reporting layer is downstream of production and upstream of nothing. Its figures
are descriptions of what happened. They are never inputs to the model, the signal, a threshold, a feature
choice, an algorithm choice or a registered checkpoint.

## 1. Where everything comes from

Every figure is derived, deterministically, from rows that already exist. Nothing is duplicated and
nothing is stored.

| table (append-only unless noted) | columns read | used for |
|---|---|---|
| `predictions` | id, as_of, cutoff_at, fetched_at, **created_at**, versions, signal, overall_score, overall_confidence (+ its components), close_price, price_source, price_is_synthetic, AI model ids, explanation present?, number of news items, run_meta | runs, signal statistics, health, timing |
| `predictions` (one hour, on request) | explanation, category_scores | the single-run detail view |
| `prediction_outcomes` | prediction_id, horizon_hours, status, price_at_horizon, pct_change_from_prediction, **checked_at** | outcome per run and horizon; graded / unavailable |
| `shadow_move_size` (outcome columns written once) | as_of, cutoff_at, fetched_at, **created_at**, model_version, status, features, p_calibrated, threshold, horizon_hours, outcome_*, **outcome_checked_at** | the move-size probability, its outcome, calibration, breakdowns, checkpoint progress |
| `shadow_run_errors` | occurred_at, expected_as_of, step, error_type (**not** the message) | health |
| `backend_state` (the one mutable cache) | contract_version, generated_at | health: how fresh the published snapshot is |
| `schema_meta` | schema_version | health |

Not read: news headlines, raw indicator snapshots, and the text of stored error messages. A stringified
exception is not something to publish; `agent/api/state.py` follows the same rule.

**Not observable from the database** (the contract says so rather than guessing): the healthchecks.io
heartbeat, the GitHub watchdog's runs, and the hourly job's total wall-clock time. What *is* derivable per
run: `start_lag_seconds` (candle close → data fetched, about 12.5 minutes by design, because the run starts
at :12) and `analysis_seconds` (data fetched → row saved).

## 2. How to call it

Locally, with the project's `.env` (the connection is forced read-only, section 6):

```
python -m agent.reporting latest
python -m agent.reporting runs [--limit 24] [--before <ISO hour>]
python -m agent.reporting run --hour <ISO hour>
python -m agent.reporting statistics
python -m agent.reporting health
python -m agent.reporting all
        [--at <ISO time>]   the record exactly as it stood at that moment (default: now)
        [--pretty]
```

The same views are plain Python functions in `agent/reporting/views.py`. They take the records
(`agent/reporting/source.load()`) and a moment `at`: `latest_run`, `recent_runs`, `run_at`,
`signal_statistics`, `move_size_statistics`, `move_size_breakdowns`, `health`, `report`. `document()` wraps
any of them in the envelope below. A future service can call these directly; it should not re-implement them.

## 3. The envelope (every output)

```json
{
  "reporting_contract_version": "1",
  "kind": "latest | runs | run | statistics | health | all",
  "as_known_at": "ISO time the view describes",
  "generated_at": "ISO time it was computed",
  "read_only": true,
  "descriptive_only": true,
  "never_use_for": ["tuning ...", "choosing features ...", "changing ... a registered checkpoint", "trading ..."],
  "limitations": ["the same list as contract v1 (agent/api/state.py)"],
  "body": { }
}
```

All times are UTC ISO strings. Numbers that are not finite are `null` (JSON has no NaN). Returns are
fractions: 0.0044 means +0.44%.

## 4. "As known at": the leakage boundary

Every view is computed by `views.known_at(records, at)` first, which keeps only what had been recorded by
`at`:

- a run appears once its row was saved (`predictions.created_at ≤ at`);
- an outcome appears once it was recorded (`prediction_outcomes.checked_at ≤ at`), and a shadow outcome
  once `outcome_checked_at ≤ at`; before that, it is `pending` or `overdue`;
- the published snapshot appears only if it was generated by `at`. It is overwritten hourly, so a view of
  the past says it is not available rather than show today's.

So a view of Monday 10:00 is the same on Monday and a year later. A 24-hour outcome recorded on Tuesday
cannot appear in it. `tests/test_reporting.py` rewrites every outcome recorded after a moment and
requires the view of that moment to be identical to the character.

## 5. The views

### A. Latest run, and B. run-by-run history

`latest`, `runs` (newest first; page backwards with `--before <next_before>`), and `run --hour` (adds the
explanation and the category scores). Each run carries:

| field | meaning |
|---|---|
| `hour`, `information_cutoff`, `data_fetched_at`, `saved_at` | the reference candle, its close, when data was fetched, when the row was saved |
| `timing` | `start_lag_seconds`, `analysis_seconds`; `job_wall_time_seconds` is `null` (not stored) |
| `signal` | BUY/HOLD/SELL with `evidence_status: no_demonstrated_predictive_value` |
| `overall_score` | `kind: score`, `is_probability: false` |
| `confidence` | `kind: heuristic`, `is_probability: false`, with its two components |
| `price` | the reference close (USD) |
| `versions` | pipeline, scoring, the two AI model ids, code commit |
| `run` | `status` ok/degraded + `problems`; price source, `fallback_used`, `price_is_estimated`, completeness, news (available, items, error type, failed sources), explanation available, `database_role` |
| `outcomes` | one entry per **registered** horizon (1, 6, 24, 72, 168 h: the outcome tracker's list, nothing invented) |
| `move_size` | the research shadow model's probability for that hour, kept separate from the signal (below) |

**Outcome states** (the same for the direction record and the shadow model):

| state | meaning | fields |
|---|---|---|
| `graded` | recorded | `return`, `direction` (the registered binary label: `UP` if return > 0, else `DOWN`), `matured_at`, `checked_at`; shadow: `large_move` |
| `pending` | the target candle has not closed, or closed less than an hour ago | `matures_at` |
| `overdue` | due for over an hour but not recorded (the tracker runs hourly) | `matures_at` |
| `unavailable` | the target candle is missing from the exchange's history; never retried | `reason` |

`matures_at` is the target candle's close: `hour + horizon + 1 h`.

### C/E. Direction signal statistics (`statistics` → `signal`)

For runs of the current pipeline (0.2.0; older rows are counted as excluded): signal counts, and for each
registered horizon and for BUY, HOLD, SELL and **ALL** hours:
- graded / pending / overdue / unavailable counts;
- `share_followed_by_a_rise` with a Wilson 95% interval;
- mean and median return.

The ALL row is the comparison that matters: a signal whose share looks different from ALL on a small
sample is still no evidence. **None of this is trading performance**, and the signal was tested on 68,619
historical hours and showed no predictive value (E001, E017). Every block repeats that. The confidence
number is a heuristic, not a probability, so **no Brier score or calibration is computed for it**.

### D/F. The shadow move-size model (`statistics` → `move_size`)

- `row_states` (graded, pending, overdue, outcome_unavailable, no_probability) and `not_prospective`.
- `running_figures` over every prospective graded hour known at the time:
  - Brier and the Brier of the observed rate;
  - `brier_rel_gain`, ECE, calibration bins (stated vs observed, Wilson interval, `enough_rows` from 100
    rows, as rule 4), accuracy, and Spearman ρ with the move size;
  - block-bootstrap intervals from 192 hours.
- `checkpoint_progress`: the count, the next checkpoint, the hours remaining, an ETA (one hour per hour,
  none lost), and which registered readings exist on disk.

These use **the registered checkpoint's own code**: `prospective_graded` for which hours count and `core`
for the mathematics. So the running figures cannot drift from the checkpoint, and a test pins them equal.
They are still **not** the checkpoint. A checkpoint reads exactly the first N hours
(`research/LIVE_EVALUATION.md`), and the only verdicts are E012 at 2,000 and E013 at 5,000 hours. The
checkpoint's pass flags are deliberately left out of this contract, because on a running sample they
would read as verdicts.

### G. Breakdowns (`statistics` → `move_size_breakdowns`)

These use the checkpoints' own slice definitions; no new regime is invented:
- UTC six-hour blocks and weekday/weekend (the 2,000-hour slices);
- volatility regime of the previous 168 h against the terciles frozen on development data (the 5,000-hour
  slice);
- the last 168 graded hours against earlier ones (a display window, not a regime).

Each group carries its own sample label. Hour blocks are read against the family's known development
offsets (E027), not against zero, and multi-week calibration drift is ordinary for this family (E029).

### H. System health (`health`)

- The status and its problems.
- The last run: hour, saved at, freshness by `agent/healthcheck`'s definition, database role, commit.
- Per window (last 24 h, last 7 days, all time): runs, missing hours (the weekly report's expected-hours
  rule), fallback-price runs, runs without news, partial news failures, runs without an explanation, and
  the median and maximum timings.
- The list of missing hours. They are never backfilled; the go-live weekend's are permanent.
- Outcomes: overdue by horizon, outcomes recorded before their candle closed (must be 0), and rows for
  unregistered horizons (must be 0).
- Shadow: rows, hours without a shadow row, and errors (step and type only).
- The published snapshot's age and the schema version.
- `external`: heartbeat, watchdog and job wall time, each `observable_here: false`, with where to look.
- Checkpoint progress.

## 6. Small samples: every figure carries its evidence

Every statistic has a `sample` object:

| n | `level` | `intervals` |
|---|---|---|
| < 192 | `too_few_to_conclude` | `not_computed` |
| 192 – 1,999 | `early_intervals_optimistic` | `shown_but_too_narrow` (E025: about 9% false positives at 500 h) |
| ≥ 2,000 | `enough_for_nominal_intervals` | `nominal` |

`is_verdict` is always `false`, and every level has a plain-English `headline`. A UI must show `n` and the
headline next to every number. Only one field in the whole contract has `is_probability: true`: the
shadow model's calibrated probability. A test walks every output to keep it that way.

## 7. Isolation from production: what makes it impossible to become part of the prediction path

| guard | proven by |
|---|---|
| Nothing in `agent/` (outside `agent/reporting`), `run.py` or `tools/` imports it | `tests/test_reporting_separation.py` (AST scan + a probe that must be detected); mutation: the orchestrator imports it |
| No workflow runs it | same test file; mutation: the hourly workflow runs it |
| It imports only reviewed read-only names (an allowlist: no `save_*`, `track_*`, `publish`, `run`, `main`) | same test file |
| Its SQL is SELECT-only: no INSERT/UPDATE/DELETE/DDL, and no `SET`, `set_config` or `TRANSACTION` that could undo read-only mode; no `commit`, `executemany` or file writes | same test file; mutation: a write statement |
| Only one function opens a connection, and it makes the **server** hold it READ ONLY, failing closed if that does not stick | same test file (a fake connection); mutations: read-only off, fail-closed removed |
| The database itself refuses INSERT, UPDATE and CREATE through that connection, even as the owner role | `tests/integration/test_reporting_readonly.py` (real Postgres, scratch schema) |
| No later outcome can reach an earlier view | `tests/test_reporting.py`; mutations: three leakage paths |
| No tiny sample labelled as evidence; no pass flag published; no error text published | `tests/test_reporting.py`; mutations for each |

## 8. Updates

There is **no scheduler and no new job**. The views read the record the hourly system already writes, so
they are current whenever they are asked. The published snapshot (`backend_state`, contract v1) remains
the only thing the hourly job writes for display.

## 9. For the future frontend (not built)

The UI's statistics page should render these documents as they are, including `sample`, `evidence`,
`never_use_for` and `limitations`, and never recompute or relabel them. How the phone reaches them is a
**separate access-control decision, deliberately not taken now**:

- The Supabase public API stays closed (RLS on, no policies, API roles revoked). It is not reopened to
  make a dashboard easier.
- The recommended design, when a UI exists, follows the contract-v1 pattern:
  - a step at the end of the hourly job publishes `python -m agent.reporting all` (and a bounded run
    history) into its own derived-cache table, never into a record table;
  - the UI reads it through Supabase Auth with **one** narrow read-only RLS policy for the owner's own
    signed-in account, never the anon key.
- Before building it, it must be proven that:
  - the step runs after the live record and the self-check, and can never fail the job (the publish-step
    rule);
  - its database role can write only that cache table;
  - the table is excluded from every input path;
  - the drift check and the public-API detector cover the new table and policy.
- Any mechanism that exposes run history outside the account holder needs its own review. The history
  contains nothing secret, but it is the user's.

## 10. What must never be done with these statistics

- Tune, refit or recalibrate any model on them, or select features, thresholds, horizons, targets or
  algorithms from them. The prospective record judges the frozen model; it never shapes it.
- Treat a running figure as a checkpoint, or read one before a registered checkpoint to decide anything.
  The checkpoints read fixed prefixes, exactly as registered.
- Present the BUY/HOLD/SELL record as trading performance, or the confidence heuristic as a probability.
- Use them to trade. This system does not trade and is not financial advice.
- Import `agent.reporting` from anything that runs in production. The tests fail if anyone does.
